# 自定义分流订阅：规则来源核验与模块方案

设计日期：2026-09-07。状态更新：2026-09-08，已实现，4.12.0 发布执行中；此状态不表示远端镜像已推送或服务器已升级。

下文保留设计阶段的建议、备选路线和来源核验记录，不将所有设计选项视为本版已交付能力。实际实现范围见 [4.12.0 发布说明](../../RELEASE-4.12.0.md)，本地验证见 [预览记录](../../REVIEW-4.12.0-preview.md)。本文与配套来源清单不被运行时加载。

## 1. 产品定位与流程

新增独立的「自定义分流订阅」页面。管理员输入现有订阅，选择新的规则目录与节点策略；CoralBay 提取节点、重新构建分流配置，为其他代理客户端输出可持续更新的链接。接收者只需按目标软件支持的方式导入。

参考网站负责给 Nextin 导入规则模板，而本模块负责生成含节点、策略组和规则的客户端配置，不依赖 Nextin、其扩展字段、内置规则包或检测脚本。

建议使用以下连续流程：

1. 输入方案名称与原始订阅；可复用现有多订阅合并能力。
2. 选择目标客户端，抓取并展示真实节点、协议和可用输出范围。
3. 从新规则目录勾选服务；提供分类、搜索、基础推荐组合、源条目预览。
4. 设置全局节点范围：地区、包含/排除条件，排除套餐和流量提示项。
5. 设置各规则的策略：跟随全局、单独选择节点、直连或拦截；支持批量修改与恢复继承。
6. 设置未命中流量的去向；预览策略组实际匹配节点、规则顺序和最终配置。
7. 校验通过后保存并发布方案，生成各目标客户端的固定链接。

方案详情提供修改、复制、停用、重置交付令牌、最近生成状态和版本信息。展示导入方式、复制链接、二维码与下载；只有已经核实协议的客户端才显示一键导入。

### 链接的更新语义

- 原始节点更新：下一次客户端更新时，抓取最新订阅并应用已保存方案，按有效缓存间隔合并重复请求。
- 用户修改方案：先生成候选配置并校验，成功后原子切换已发布版本；原链接保持不变。
- 上游规则更新：新模块独立同步并验证源快照；后续生成使用新快照。已经交付的配置引用不可变的规则版本，避免一次配置混用两次同步内容。
- 停用或换令牌：明确阻止对应旧交付地址再次拉取；不影响旧模块链接。
- 规则同步失败：保留新模块上一份有效规则，不触发旧模块回滚。节点抓取失败时不发布空配置；如提供上一份有效配置，需有明确的保留期限与可见的过期状态。

### 不照搬参考站的默认分类含义

`geosite/tracker` 对应 BT Tracker 集合；参考站把它描述为隐私追踪器并默认拦截，不能直接采用。新目录应标为「BT Tracker」，作为用途明确的可选规则，默认不纳入广告/隐私拦截组合。[官方构建流程](https://github.com/MetaCubeX/meta-rules-dat/blob/master/.github/workflows/run.yml)记录了 PrivateTracker 和 TrackersListCollection 来源。

例如 Bilibili、iCloud 等规则的默认去向也应结合用户方案确定；上游提供的是匹配集合，用户方案决定直连、代理或拦截。地区筛选依据节点命名，不能冒充真实出口地域或服务解锁检测。

### 新规则的数据方式

- 新模块直接同步 MetaCubeX 的固定版本，不通过 Nextin Hub API 取得生产规则。
- 建议以同一 MetaCubeX 上游的 `geo/geosite/classical/{file}.yaml` 作为域名规则规范化输入，IP 仍采用 `geo/geoip/{file}.yaml`。保留规则名、来源、类型、条目数、提交、摘要和同步时间。
- 这是对参考站 domain 子集的语义补齐，而不是完全相同的匹配范围。官方转换器将关键词和正则保留在 classical 中，不导出到普通 domain YAML/MRS；已实际抽查同版本 Google、private、ads-all 三项 classical。实现同步前仍需逐项验证所有选定 classical 文件、内容和目标客户端支持范围，不能把此次 78 项普通 YAML 可达性验证当成 classical 全量验证。[转换器依据](https://github.com/MetaCubeX/meta-rules-converter/blob/main/input/geosite.go)
- 能使用 MRS 的客户端可对纯域名/IP 部分使用经验证的同版本 MRS；关键词、正则等剩余规则使用客户端支持的补充文本规则集或原生规则。其他客户端由可读源转换为各自支持的规则格式。不可将 classical 全部规则直接压成 MRS 并声称无损。[MRS 格式支持范围](https://wiki.metacubex.one/config/rule-providers/)
- 上游的后缀、精确域名、通配符、正则、关键词、IPv4/IPv6 等语义必须按实际内容识别；不能静默丢弃无法映射的条目。
- 保留上游来源与许可文件，参考网站 UI 或描述不作为客户端匹配语义的依据。

## 3. 新旧隔离与可复用能力

以下路径为设计示意，尚未注册：

| 部分 | 新模块建议 | 旧模块处理 |
| --- | --- | --- |
| 页面 | `/routing`，独立页面模块 | 保留现有页面及旧 hash 导航映射 |
| 管理 API | `/api/routing/...`，沿用管理员会话 | 旧 API 行为不变 |
| 方案与统计 | `$DATA_DIR/routing/routing.sqlite` | 不改写旧表与旧生成历史 |
| 规则快照 | `$DATA_DIR/routing/rules/releases/{revision}/` | 不复用旧 `current` 与 `_converted` |
| 更新发布 | 新模块独立任务、锁、状态与当前版本指针 | 不改变 666OS 的同步/回滚过程 |
| 规则资源地址 | `/_routing/rules/{revision}/{rule-id}` | 旧 `/mihomo/`、`/surge/` 等保持原义 |
| 新订阅交付 | `/routing/sub/{token}/{client}` | 旧 `/sub` 的签名、停用和统计不变 |

共享能力可以包括登录、受约束的网络抓取、节点协议转换、只读地区匹配算法、二维码和基础 UI。共享能力不等于共享规则内容或历史记录。

特别注意：当前地区表把英国/德国等合并为欧洲，并不完全对应参考站的国家列表。若新增独立国家分类，应使用新版本匹配目录或显式配置，不直接改动旧表而导致旧模板筛选结果变化。

后续可在旧转换页提供「复制为自定义分流方案」入口。复制订阅参数并创建新记录；新规则选择使用新目录，旧规则 ID 不自动映射，旧记录和旧链接继续保留。首期不强制迁移历史数据。

### 需要专门处理的代码边界

- `main.go` 的 `convertSubscription` 同时承担旧转换行为和兼容修复。新模块只能复用经过拆分验证的节点转换能力，不能隐式带入旧远程预设、旧 Pro_cn 策略或默认规则。
- `subscription_usage.go` 的 `usageID()` 仅按 query 计算，不包含 path。新路径型链接必须使用独立 `link_id/profile_id`，不能直接登记进旧统计表。
- 当前 `/sub` 将转换参数放入签名查询字符串；新方案需要持久化的方案 ID 与交付令牌，才能实现编辑后 URL 不变。用户收到的地址无需包含原订阅 URL。
- `sync.sh` 的发布链路围绕 666OS，不能把新源直接塞进其现有发布目录。

建议新数据库分别保存方案、订阅源引用、方案版本、目标客户端交付记录、构建状态和规则快照引用。一次发布记录需能追溯所用方案版本、规则快照及生成器版本。

## 4. 生成与客户端支持

生成顺序：受控抓取原始订阅 → 解析并保留节点协议字段 → 合并与去重 → 全局筛选 → 各业务策略组筛选 → 新规则编译 → 客户端渲染 → 校验 → 发布。

对完整原始配置，输入阶段主要提取节点；DNS、策略组和路由由新方案及对应客户端的配置骨架生成。不能用正则替换文本来拼凑整个配置，也不能强制所有协议先降级到某个客户端的节点格式而静默损失字段。

必须校验：

- 目标客户端是否支持输入协议及关键 TLS/Reality/传输字段。
- 每个组是否真的有节点；零匹配时展示原因，并要求选定明确兜底或阻止发布，不静默变成直连。
- 精细规则与集合规则的顺序，例如 Gemini 在 Google 集合之前、单个媒体服务在媒体集合之前。
- 私有网络、用户明确指定的直连例外、广告规则、细分业务、宽泛集合与最终兜底的相对顺序；提供可解释预览。
- 规则引用、策略组引用、重复名称、循环引用和文件语法。
- 不同客户端的语义是否等价；不支持的规则类型或功能必须被明确标记。

「支持转换为某软件节点订阅」不等于「支持该软件的完整分流配置」。

| 客户端范围 | 交付设计 |
| --- | --- |
| Mihomo / OpenClash、Stash | 第一批建议：含节点、策略组、规则和 DNS 的可更新完整配置 |
| Surge、Loon、Surfboard、Egern | 使用各自配置语法，逐个完成原生规则与协议验收；可以复用已有语法适配经验，但规则和组使用新模块生成 |
| sing-box / Hiddify | 单独实现 JSON 路由、出站与规则集生成，声明并验证版本范围 |
| Shadowrocket、Quantumult X 等 | 逐软件核实远程配置及节点更新机制；需要分开管理节点和配置时提供配套地址与导入步骤 |
| 通用 URI / Base64 | 只承载节点；不能把它标为完成了自定义分流 |

新模块不需要因此引入用户注册、多租户或任意脚本执行。节点服务解锁检测可在以后独立规划，不作为规则订阅模块的前置条件。

## 5. 导航与页面分类

当前真实管理页面是 `web/admin.html`，通过 `web/app.js` 切换 6 个横向标签：概览、PPanel 模板、MihomoPro 覆写、规则资源、订阅转换、日志与版本。目前没有抽屉；订阅管理由 JavaScript 动态追加到转换表单底部。

建议桌面采用分组侧栏，手机采用同一分组的抽屉；主要分组不超过两层，页面内的格式筛选仍使用小标签。

| 分组 | 子页面 |
| --- | --- |
| 总览 | 运行概览 |
| 订阅服务 | 普通订阅转换；自定义分流订阅；订阅管理 |
| 客户端配置 | PPanel 模板；OpenClash / MihomoPro 覆写 |
| 规则与配置源 | 666OS 规则资源；MetaCubeX 分流规则源；远程配置库 |
| 系统维护 | 同步与计划；程序更新；日志与版本 |

交互边界：

- 订阅管理从长表单拆为独立页，内部以「普通转换」「自定义分流」两个独立数据视图区分；默认操作只作用于当前类型。
- 新规则源页只显示本模块目录、原链接、条目、版本、更新时间、校验及同步状态，不混进 666OS 列表。
- 远程配置库保留原有 `.ini` 预设含义，普通转换页继续提供预设选择器；不把它与原始规则集混称为规则源。
- 概览只呈现摘要与快捷入口；同步页按源明确区分 666OS 和 MetaCubeX，旧同步按钮不会同时更新新源。
- 首次整理可以只调整导航、拆出订阅管理、新增两页，避免同时改写所有旧页面。
- 保留 `#overview`、`#templates`、`#overwrite`、`#rules`、`#subscription`、`#activity` 的旧入口映射。
- 新页面按需加载。当前 `refreshAll()` 同时加载多页的做法不扩展到新模块，防止新源失败导致全站显示连接异常。
- 页面操作显示本页结果或统一通知，不再把所有反馈写到概览的 `#message`。

## 6. 建议实施顺序与验收

1. 落实独立来源目录、同步快照和规则含义；建立不依赖旧规则的新模块基础。
2. 完成方案持久化、节点导入、逐规则策略及固定链接生成，优先验收 Mihomo/OpenClash 与 Stash。
3. 接入独立分流页面、规则源页和分组侧栏；拆出订阅管理，保留旧入口兼容。
4. 按客户端完成其余完整配置适配；再考虑旧功能的「复制为新方案」入口。

验收依据是完整用户流程，而不只是能下载 YAML：

- 原订阅节点变化后，同一新链接按既定策略重新分组。
- 修改、保存方案后，已导入客户端更新同一链接得到新配置。
- 已导出配置只引用新模块规则，不出现旧 666OS 内容或 Nextin 专属依赖。
- 规则集合与节点筛选符合预览，空组和不支持协议被明确处理。
- 新模块同步失败、停用、统计清理和回滚均不修改旧规则、旧链接、旧历史。
- 旧导航地址、旧订阅拉取、旧模板下载、666OS 同步与回滚通过回归验证。
- 客户端内实际验证策略选择、规则命中和更新行为；语法检查不能替代客户端验收。

本次仅完成源码与公开来源调查，没有进行客户端运行验收。
