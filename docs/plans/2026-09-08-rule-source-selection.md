# 规则资源本地保存与来源选择：升级规划

日期：2026-09-08。基于 4.12.0 核对后形成规划。4.13.0 已完成 A、B 的代码与验证，并实现 C 中的配置依赖识别；D 与完整第三方依赖镜像留待后续。以下保留原始规划，实际范围见 [4.13.0 说明](../../RELEASE-4.13.0.md)。

## 1. 建议结论

两套规则库都在 CoralBay 服务器保存独立、完整的可用副本。在「规则与配置源」查看本地副本和上游来源，在「订阅服务」为每个订阅方案选择使用方式。

建议新方案默认使用「CoralBay 本机」，另提供「上游来源」。来源选择保存在各自方案中；资源页可以带着当前选择进入新建订阅，但不设置会追溯修改全部旧订阅的全局开关。

这里的「本地」指部署 CoralBay 的服务器。完成首次同步后，规则可以在上游不可达时继续由服务器提供；客户端仍需访问 CoralBay，节点订阅更新也可能需要网络。首次安装没有规则数据时，需要完成初始化同步，或导入预先准备的快照包。

首期保存范围是项目已管理的 666OS 规则及其生成依赖、MetaCubeX 当前 78 项目录，不是无边界镜像两个上游仓库的全部历史和资源。

## 3. 页面与交互

保留现有导航分类，集中改善两个资源子页，无需再次重排全部页面。

| 位置 | 负责的工作 |
| --- | --- |
| 规则与配置源 → 666OS 规则资源 | 666OS 本地副本、上游信息、格式和转换关系、同步与版本 |
| 规则与配置源 → MetaCubeX 分流源 | MetaCubeX 本地副本、上游信息、服务目录、同步与版本 |
| 订阅服务 → 自定义分流订阅 | 选择服务规则、规则交付来源、节点策略，预览并保存方案 |
| 订阅服务 → 普通订阅转换 | 保留配置文件来源选项；根据预设实际能力展示规则来源选项 |

两个资源子页统一采用以下布局：

1. 顶部概览：本地就绪数量／应有数量、本地版本、最近同步时间、最近上游检查时间、是否发现更新、磁盘占用。
2. 列表：规则名称、分类、格式、条目数、本地状态、上游检查状态、版本差异。
3. 点击规则打开详情抽屉，包含「本地副本」「上游来源」「版本差异」三个页签。
4. 操作：检查上游更新、同步本地、查看／搜索条目、下载文件、复制地址、使用此规则创建订阅。

本地详情展示文件实际版本、文件大小、摘要、来源地址、同步时间和可读内容。上游详情展示仓库、分支、固定提交、原始文件地址、最后检查结果和该版本内容；“尚未检查”“访问失败”“本地副本缺失”分别显示，不合并为一个“离线”状态。

查看上游的临时读取结果独立缓存，不改变已发布的本地版本。详情默认分页，支持搜索；大型规则不一次性塞入抽屉。检查分支最新版本和检查某个固定文件分开记录，避免只检查首页就把全目录标为可用。

差异对比需要选择明确的两个版本。同格式原始文件可以比较摘要；规范化规则比较新增、删除条目。二进制 MRS 无法直接解析时显示元信息；关联的 geo 可读文件标为「关联源」，不能当成该 MRS 的精确反向还原。

## 4. 订阅中的来源选择

### 新建自定义分流方案

建议流程：输入节点订阅 → 选择客户端 → 选择服务规则及来源 → 设置策略 → 预览 → 保存与复制交付链接。

在选择服务规则的顶部增加「规则下载来源」：

| 选项 | 实际行为 | 页面说明 |
| --- | --- | --- |
| CoralBay 本机，默认 | 客户端从本服务的固定版本地址下载规则集合 | 使用服务器保存的规则副本 |
| 上游来源 | 客户端从同一规则、同一提交的上游地址下载集合 | 客户端需要能够访问该上游地址 |

两种选项使用同一已校验版本，尽量做到只改变下载地址，不改变规则内容、优先级、节点筛选或策略。选择上游也继续维护本地副本，以便核验和后续主动切换。

「规则库」和「规则下载来源」是不同概念。首期自定义分流继续使用 MetaCubeX；普通内置方案继续使用现有 666OS 体系。不能因为两边都有 Google 就自动把一套规则替换为另一套。未来增加跨库选择时，应显式创建草稿、重新选择规则并预览。

预览与方案详情显示：规则库、下载来源、实际规则版本、生成时间，以及哪些依赖仍来自外部。如果用户选择严格本机方式，但有必要规则没有本地副本，应列出缺项并提供同步入口，不自动改用上游。

### 为什么 MetaCubeX 需要调整输出

当前配置直接内嵌所有规则，客户端没有独立的规则下载地址。如果只在服务端增加「读缓存／重新抓取」开关，用户看到的“来源切换”并不会改变客户端访问的地址。

建议为新方案增加 `rule-providers` 与 `RULE-SET` 输出：域名规则使用保留关键词、正则的 classical YAML；IP 规则使用 ipcidr YAML，并保留 `no-resolve`。本机保存已验证的原始字节，上游引用相同提交，避免换格式时缩小匹配范围。Mihomo 和 Stash 官方文档均提供相应集合能力；实际交付仍需针对目标客户端验证。[Mihomo 规则集合](https://wiki.metacubex.one/config/rule-providers/)、[Stash 规则集合](https://stash.wiki/rules/rule-set)。

第一版优先 YAML，避免为节省体积将包含关键词、正则的 classical 集合直接换成 MRS。正则中带逗号、量词、IPv4/IPv6 和直连规则优先级，需要专门核对从内嵌输出迁移后的行为。

是否允许上游直引，按「来源＋具体资源＋格式＋客户端」记录支持状态。某个客户端不能完整读取原始文件时，暂不开放该组合；本机做过兼容转换的文件应单独标记，不能宣称与上游原文件字节相同。

### 666OS 与普通转换的支持边界

666OS 的原始发布文件与本机镜像有直接映射，可在消费这些文件的客户端模板中增加来源选择。生成前固定对应 release 提交；geo 依赖另外固定 geo 提交，不能把两个分支当成一个版本。

模板选择通过新增模板变体或版本地址实现。现有 PPanel 等共享模板的地址和默认含义保持不变，避免一个订阅选择上游后，其他引用同一模板的订阅也被修改。

项目自己生成的 `/_converted/...` 资源没有天然对应的上游同路径文件。内置 MihomoPro INI 正在使用这些派生规则，不能简单替换域名来实现“上游模式”。

实施时给预设建立能力清单：

- 有等价上游文件：允许客户端下载地址切换，保证格式和语义对应。
- 规则在生成时被内嵌：如果支持从上游读取，应单独标为「生成时规则读取来源」，仍通过既有转换器处理并校验；不能称为客户端下载来源切换。
- 只有本服务生成的派生格式：维持本机交付，显示原因；后续补齐适配后再开放相应选择。
- 第三方 INI：原有选择更名为「配置文件来源」。解析其规则依赖并显示本机／外部覆盖情况；在依赖尚未全部镜像前，不提供“全部使用本机规则”的承诺。

没有公开可逆源而产生的零条目占位文件，应标明「无可读源／零覆盖」，不能因为文件存在就当成完整有效规则。

这让两个规则库都可查看、保存和下载，同时避免一个表面统一的开关隐藏不同的真实行为。

## 5. 本地资源、同步和版本

两套资源继续各自维护目录、同步任务、锁和发布指针。界面与只读元信息可以复用；不合并数据表、规则 ID 或现有发布路径。

MetaCubeX 在原有快照旁新增原始 YAML 和资源清单，形成「原始文件＋规范化条目＋版本清单」。原始内容摘要应与实际交付字节对应；从 JSON 重建出的 YAML 必须标为生成文件，不能冒充上游原件。

为 MetaCubeX 增加独立的完整目录定时同步，建议每日一次并支持手动同步。666OS 沿用当前同步节奏和发布机制。候选版本全部通过检查后才原子发布；某项失败保持上一完整版本，明确显示失败项与最后成功时间。

严格本机方案构建只读取已发布快照，即使快照超过检查周期也不触发上游请求；过期检查由独立任务负责。当前会按需刷新的加载逻辑只保留给旧方案兼容路径，本地详情也使用纯读取接口。

资源清单至少记录：来源库、规则 ID、上游仓库及文件、提交、原始摘要、格式与 behavior、条目数、文件大小、下载时间、校验结果、生成器版本，以及本地交付地址。保留上游许可及归属信息。

新资源 URL 包含来源、版本与文件名，避免覆盖已经交付的版本；现有 666OS 公共 URL 保持原有含义。示意 `/_rule-resources/{source}/{version}/{file}`，实施时再确定路由名称。

新方案默认在重新生成订阅时跟随本地已发布版本；单份生成结果中的引用固定版本。检查上游、同步本地、重新生成订阅是三个不同动作。新建快照不会让客户端持有的旧配置突然混用另一版本；客户端重新更新订阅后取得新的规则引用。

历史清理必须考虑已经交付的地址：当前版本、正在构建的版本、方案固定版本和已交付引用不能仅按目录日期删除。首期不自动清理被交付引用的版本，并设置磁盘告警；后续明确保留期限和失效规则后，再开放自动清理。现有 666OS 仅保留少量历史版本的逻辑不能直接用于新版本交付地址。

如果需要“新服务器首次启动就能断网使用”，另提供带清单和摘要的快照导出／导入包。这与同步后本地可用分开交付，不默认把整个上游仓库打进 Docker 镜像。

## 6. 兼容已有订阅

旧分流方案缺少新字段时，继续使用既有内嵌输出和规则更新策略。新默认值只用于新建方案；升级服务不会批量改写旧方案、节点来源、规则选择或交付令牌。

新方案明确保存 `rule_delivery` 等字段，区分 `inline` 与 `provider`、本机与上游，并记录实际生成版本。现有 `sources` 字段表示原始节点订阅，不能拿来存规则来源。

旧分流方案主动切换时，先预览、验证候选配置，再按方案版本原子保存；生成缓存同时失效。成功后保留现有 `/routing/sub/...` 链接，客户端下次更新取得新内容。失败继续保留原方案。

普通转换 `/sub?...&sig=...` 是带签名的参数链接。保留旧参数与签名验证行为；新的来源参数加入签名和缓存标识。改变此类链接设置时生成新签名链接，不能承诺旧链接会自动变成新设置。

回滚发布保留升级前的程序和数据备份。新增数据结构优先使用可兼容字段；若旧程序无法理解新方案，回滚时恢复对应备份，不让旧程序把未知设置默认为另一来源。

## 7. 分阶段实施

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| A：完整本地资源与双源详情 | 补齐 MetaCubeX 原始文件、完整目录同步、两个资源页详情及搜索、独立上游检查 | 两套已管理资源在同步完成后可从本地读取；查看详情不改变活动版本 |
| B：订阅使用来源 | 新分流方案本机／上游集合输出、同版本交付、方案级设置及旧方案兼容；666OS 原始文件模板建立对应切换 | 选择真实改变支持范围内的规则地址，预览可核对；旧方案升级前后行为保持一致 |
| C：配置依赖适配 | 普通预设标注配置来源和规则来源、分析 INI 嵌套依赖、逐项补齐 666OS 派生格式与外部预设适配 | 支持清单明确；选本机时能够证明所需规则均为本机提供，否则明确提示不支持 |
| D：版本管理增强 | 差异详情、手动固定版本、回滚、快照包导入导出、受引用约束的清理策略 | 可复现指定版本；恢复后地址与内容一致；清理不删除受保护版本 |

建议 A、B 作为下一次核心升级，C 按预设逐步开放，D 随后补齐。元信息差异在 A 提供，完整条目差异放在 D。不必把新来源选择与再次重构全部导航绑定。

## 8. 发布前验收

1. 本地可用性：屏蔽规则上游，使用固定测试节点订阅；本机规则详情、资源下载与新方案生成成功，不隐式访问规则上游。
2. 缺失与失败：首次没有副本、单条损坏、同步超时、候选版本不完整时，不发布空集合，不偷偷改用其他来源，也不覆盖最后有效版本。
3. 同版本等价：两种地址下载得到相同原始文件摘要；核对客户端实际加载的规则数量，并对域名、关键词、正则、IPv4/IPv6、`no-resolve`、直连优先级和最终兜底验证规则命中，不能只看配置检查是否通过。
4. 客户端交付：验证 Mihomo／OpenClash 所用内核，并单独验证 Stash 的集合读取和实际命中；不能把 Mihomo 语法检查当成所有客户端验证。
5. 生成时不依赖线上自请求：校验候选配置时用候选文件构建临时校验环境；资源发布成功后再发布引用该版本的配置，避免半成品 URL。
6. 旧数据兼容：使用升级前普通签名链接、旧分流方案和两个规则目录做回归；检查令牌、节点筛选、策略、停用状态与历史数据。
7. 操作边界：只浏览上游不发布新本地版本；一个方案切换来源不修改其他方案；666OS 同步失败不影响 MetaCubeX，反之亦然。
8. 引用与留存：方案更新、规则同步、并发下载和历史清理同时发生时，配置不会指向缺失文件；原始规则资源不包含用户节点或订阅凭据。

执行到这里才适合更新 README、搭建文档和发布说明，再按实际实施范围构建镜像、发布与升级服务。规划阶段不把这些事项标为已完成。
